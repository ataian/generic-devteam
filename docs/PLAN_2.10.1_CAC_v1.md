# Compact Artifact Contract — implementation plan

**Status:** Final planning handoff; proposed, not installed. Implementation requires a later request. **Owner:** Mariko, same profile, Astra-6.2/high; use Sol-6.2/medium or high for suitable independent work. **Repository:** `/home/mariko/projects/generic-devteam`, branch `cac`, Maker `2.10.1`, base `7910b031f195e6302022e83b48f58e83081082a1`. **Design:** [SPEC_2.10.1_CAC_v1.md](SPEC_2.10.1_CAC_v1.md). **Inputs:** [CAC-HERMES](cac/CAC-HERMES.md), [CAC-CODEX](cac/CAC-CODEX.md); previous authoring baseline TAS 1.2.0.

**Goal:** Spend fewer tokens on instructions and exchanges while allowing each recipient to take exactly the same action, for the same reason, within the same authority. Change how the agents write, not how they work. Source fidelity outranks any size target.

**Architecture:** Use a short Maker authoring reference, operative rules in each rendered Hermes SOUL, and a short native team-local Codex instruction file. Give each recurring exchange a default compact form at its writing point. Use current Markdown, templates, manifest, setup/update recipes and Python unittest suite. No shared parser, new service, role, workflow skill or mandatory report file. This plan's checklists and review aids are for the Maker change only.

## 3. Put compact forms at the existing writing steps

Implement the following as short **writing patterns**, not new actions, database schemas or exhaustive lists of allowed fields. Merge with the existing requirements at each anchor. The text after each field below describes content, not a placeholder to print. Use one-line forms for simple events, grouped facts for complex ones. Never omit an existing required negative result by treating it as an empty optional field.

| Owner / anchor | Pattern to embed | Boundary |
|---|---|---|
| Planner SOUL, planning sequence; `skills/brownfield-feature-planning/references/kanban-phase-release.md` §2 | **Title:** one genuine story. **Body:** outcome/context not in title; observable criteria; affected interfaces and binding limits; verification; dependency and exact plan/phase/root/commit bindings. | Preserve customer decisions, accepted limits and reasons, suggestion vs requirement and established native fields. Do not replace them with a link. |
| Coder SOUL, Codex task and resume | `Goal:` · `Scope:` · `Constraints:` · `Evidence:` · `Acceptance:` · `Verify:`. Resume with the relevant state/delta; keep required standing constraints. | A result contract cannot narrow the work. Preserve any additional required directions for the actual assignment. |
| Team-Codex AGENTS, result | `Change:` · `Checked:` actual result and state · `Open:` material failure, skipped check or limitation. Keep decisive evidence/reference with its claim. | Do not invent a commit for uncommitted work, report unrun checks as success, or claim independent review. Existing formal output requests win. |
| Coder SOUL, `kanban_request_review` | `Commit:` exact implementation commit · `Result:` concise outcome · `Risks / gaps:` material facts and consequences · evidence reference or required attached output. | Preserve `Tests passed` only for verified required coverage, and original RED evidence or absence of RED. Do not create a second review report. |
| Reviewer SOUL, findings and verdict | `At:` · `When / observed:` concrete failure · `Correct outcome:` · `Impact:` · `Evidence:`. Single line when clear. For closure: reviewed commit, criteria/findings closed, evidence reused, carried limits. | Separate defect, question and suggestion. Give the corrective outcome; a means is optional unless already binding. Preserve native comment/readback/transition order and exact approval metadata. |
| Sending role, existing status/clarification/block step | Normal status: changed fact and necessary next action on one line. Decision: `Question:` · `Why it matters:` · options/recommendation when the existing escalation calls for them · paused work. | No new status events. Keep task/board/reference when the destination is ambiguous; report original error, reset time/zone or uncertainty for quota. A text field never changes native state. |
| Planner SOUL, customer communication | **“Lead with the result or the decision you need. Use the customer's language. Explain the consequence and your recommendation when a choice matters. Do not repeat ticket fields or routine checks in the customer message.”** | Existing evidence remains at its original location; no new logging duty. Preserve the exact last-ticket report obligations, publication boundary, access instructions and retrospective offer. |

Example, not a new project requirement: `At: import.py:42 | When: id omitted → row accepted | Correct outcome: reject the row | Impact: invalid record stored | Evidence: missing-id test`. The reviewer states the faulty case and the target without directing the Coder to a particular implementation. Human-facing alternative for a decision: “Der Import weist die Datei vollständig zurück. Sollen gültige Zeilen trotzdem übernommen werden? Das wäre eine Änderung am vereinbarten Verhalten.” Do not force a question on a settled decision.
