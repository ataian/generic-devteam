# Devteam Interface Improvements — Review Plan

> **For workers:** Review draft only until explicitly approved. Preserve the established Planner/Coder/Reviewer routing. This document does not authorize implementation, ticket creation, live-team updates, service changes, or deployment.

**Status:** Draft for later independent review.
**Document version:** 1.0.0. This is a standalone review proposal, not a Maker release version or a replacement for an approved implementation baseline.
**Goal:** Reduce avoidable handoffs, duplicate analysis, and context transport at the Planner–Coder and Coder–Reviewer interfaces without weakening verification or customer authority.
**Architecture:** Keep Planner, Coder, Codex, and independent Reviewer. Move in-scope implementation decisions to the Coder. Keep native dispatch, event-driven Planner wakes, Mattermost accompaniment, and recovery.
**Technical basis:** Existing Hermes Kanban, Maker role templates and assigned skills, Team-Codex, and the established project channel.

## 1. Agreed direction and boundaries

This proposal records the final direction of the discussion. Earlier ideas to remove the Coder, merge Planner and Coder, remove routine wakes, or add a dedicated closing ticket are superseded.

- The Planner plans the work, obtains plan approval, creates tickets, accompanies execution in Mattermost, and coordinates exceptional recovery.
- The Coder owns ticket execution and directs Codex. Codex remains the only unit that changes project files, including tests, configuration, scripts, and product documentation.
- The Reviewer independently assesses the implementation and owns its quality verdict.
- The customer owns product decisions, scope changes, unresolved customer trade-offs, and external or operational approvals.
- Existing model, reasoning, access, infrastructure, Git, and publication boundaries remain effective.
- Implementation authority is not permission to change an approved requirement, API contract, security invariant, deployment target, or shared platform.
- The approved plan remains versioned. The existing ticket holds task decisions, blockers, handoffs, and references to original evidence. This proposal adds no mandatory evidence register or parallel reporting store.

The expected benefit is fewer internal decision handoffs and less repeated investigation. The SOOS audit is not a controlled before/after comparison. It does not establish a percentage saving for this proposal.

## 2. Interface A: Planner–Coder

### 2.1 Idea: decide where the implementation context already exists

Keep the separate roles and sessions. Give the Coder authority to settle technical implementation questions within the approved plan. A technical question must not require a second Planner investigation merely because the Planner previously owned that class of decision.

During execution, a deliberate decision escalation from Coder to Planner means that a customer decision or an approval outside the Coder's mandate is required. The Planner acts as the customer interface, not as another technical approval layer.

This contract is distinct from automatic failure and recovery events. A crash, missing capability, or `triage` event is not automatically a customer decision.

### 2.2 How to change the interface

1. Replace clauses that reserve all architecture or implementation decisions for the Planner. The Planner retains planning and approved architectural constraints. The Coder selects implementation details within those constraints.
2. Transfer the existing discretion for minor in-scope implementation decisions to the Coder during execution. Preserve agreed function, essential usability, explicit requirements, security, privacy, data integrity, permissions, cost boundaries, and external contracts. Several small decisions must not accumulate into an unapproved redesign.
3. Require the Coder to investigate Codex questions against the current repository and accepted requirements. Continue implementation after an answer within that mandate. Record consequential decisions on the existing ticket; do not create a separate approval record for every local choice.
4. Replace the Planner's execution-time duty to independently resolve routine Coder questions with a customer-clarification duty for deliberate decision escalations. The Planner checks the decision boundary and completeness of the question. The Planner does not repeat the Coder's technical investigation as a routine prerequisite.
5. Require a customer escalation to identify the missing decision, observed facts, relevant options, recommendation, effect on scope or risk, and work that remains paused. Keep the technical evidence accessible from the ticket.
6. Use native `kanban_block(kind="needs_input", reason=...)` for the proposed customer-decision pause, with the established Planner wake subscription. Keep the Coder assignment. After an explicit customer decision, the Planner records its source and scope, coordinates any approved baseline change, and uses native resumption. Verify the resulting phase and assignment.
7. Replace the old Coder-to-Planner `kanban_request_review` clarification route consistently in role and companion skill instructions. Quality review still uses `kanban_request_review` to the independent Reviewer. Do not retain both clarification routes as competing defaults.
8. Preserve native wakes and concise Mattermost updates. Routine progress uses existing results and review verdicts. It does not trigger another implementation investigation.

A vague escalation can be returned for a precise question or missing evidence. This is not permission for the Planner to silently make a customer-owned decision. Existing approvals remain usable within their exact scope; they do not need repeated confirmation.

## 3. Interface B: Coder–Reviewer

### 3.1 Idea: review-ready is not already independently reviewed

Codex implements and performs the agreed implementation checks. The Coder establishes a trustworthy handoff. The Reviewer independently decides whether the solution is correct and acceptable.

Some overlap is intentional. Both roles may inspect the same diff or test evidence for different purposes. The target is avoidable duplicate full investigation and execution, not the removal of independent scrutiny.

| Coder: establish review readiness | Reviewer: assess quality independently |
|---|---|
| Confirm task scope and the actual changes. | Assess correctness against requirements and contracts. |
| Separate task-owned and unrelated work. | Examine relevant callers, dependencies, failure paths, and regressions. |
| Confirm which checks ran and which state they cover. | Assess whether those checks prove the required behavior. |
| Resolve visible execution failures and disclose remaining gaps. | Perform required independent checks and report supported findings. |
| Hand over the exact commit and retrievable original evidence. | Deliver a verdict for the exact reviewed commit. |

### 3.2 How to change the interface

1. Narrow the Coder's post-Codex inspection to execution control and review readiness. Keep actual diff inspection, scope control, evidence validation, selective staging, and commit checks. A Codex completion message alone is not proof.
2. Remove any blanket obligation to perform a full systematic review before the independent Reviewer. The Coder still investigates concrete inconsistencies, fixes known defects, and remains responsible for the delivered work.
3. Use optional internal Codex review helpers only for a defined evidence gap or concrete risk. They are not an automatic extra review stage and do not replace the independent Reviewer.
4. Reuse original check evidence while its inputs, relevant dependencies, configuration, and conditions remain valid. Preserve the original executor and checked state. Rerun affected, insufficient, explicitly independent, or required final-state checks. A role handoff alone is not a reason to rerun every suite.
5. Preserve the Reviewer's own source assessment, acceptance duties, risk rules, and required separate passes for material critical invariants. This plan does not remove those passes or treat every repeated check as waste.
6. After `CHANGES_REQUESTED`, continue on the same ticket. The Coder directs Codex to correct the findings and affected dependencies. The Reviewer assesses the delta and accounts for every prior open finding. Resume unfinished work rather than ritualistically restarting all preparation.
7. Keep handoffs compact and complete: exact commit, scope, original evidence, actual results, reused evidence, open gaps, risk, and required next action. Describe each finding once and reference it unambiguously on return.
8. Reduce unnecessary context at authoring time. Use only verified supported retrieval paths when selecting existing ticket information. An instruction to read the latest entries is insufficient when older binding decisions are still relevant. A new slim-query API or parser framework is outside this policy change.

Evidence reuse and delta review already exist in the current rules and were visible in the SOOS audit. Implementation must remove remaining conflicting obligations and improve application, rather than add duplicate versions of the same policy.

### 4.2 Acceptance scenarios

- A Codex implementation question inside the approved scope is answered by the Coder without a Planner decision round.
- A missing product decision pauses affected work and reaches the customer through the Planner. No implementation proceeds on an ambiguous answer.
- An explicit customer answer is recorded on the existing ticket and resumes the correct task and phase once. Duplicate delivery does not duplicate execution.
- A review-ready handoff has an exact commit and attributable original check results without a mandatory Coder full review.
- A Reviewer can require additional checks for a concrete gap and can return supported defects through `CHANGES_REQUESTED`.
- A correction preserves valid evidence, refreshes affected checks, and accounts for all open findings before approval.
- A capability failure, quota pause, repeated block, or `triage` event retains a responsible recovery owner and the established wake path.
- Quality approval does not imply permission to push, deploy, repair infrastructure, or expand scope.

## 5. Expected end-to-end workflow, including failure paths

### 5.1 Normal path

1. **Customer + Planner:** clarify the request, prepare the plan and phases, and obtain explicit approval.
2. **Planner:** create baseline-bound dependent tickets, verify assignments and wake subscriptions, and hand execution to the dispatcher.
3. **Dispatcher → Coder:** start a ticket-bound execution context.
4. **Coder → Codex:** commission implementation and agreed checks. Resolve in-scope technical questions directly.
5. **Coder → Reviewer:** inspect review readiness, commit task-owned changes, call `kanban_request_review`, and verify state and recipient. Stop project changes until native return.
6. **Reviewer:** assess independently. For supported defects, record findings and call `kanban_request_changes`. The Coder corrects with Codex and requests review again.
7. **Reviewer:** approve the exact checked commit and complete the ticket through the native review outcome.
8. **Dispatcher:** release eligible successors. **Planner wake:** give a concise progress response from existing evidence. At overall completion, deliver the closing report from ticket results and review verdicts.

### 5.2 Customer escalation

`Coder identifies an out-of-mandate decision → records the question → needs_input pause → Planner wake → customer discussion → explicit decision on the ticket → native resumption → dispatcher → Coder`.

The Planner checks board, ticket, question, and current state before resumption. The customer answer authorizes only its stated scope. A changed plan baseline must be recorded and reconciled before affected execution continues. The Mattermost session coordinates the answer; it does not become the coding session.

If the Reviewer discovers a genuine requirement conflict, the Planner obtains the customer decision. Record that decision on the same ticket and preserve the applicable review/implementation return phase. Do not approve an unresolved conflict.

### 5.3 Technical failures and quota pauses

- **Recoverable command or execution error:** the Coder corrects the call or directs Codex to continue within existing authority.
- **Missing mandatory capability or platform failure:** stop affected work, record the actual error and state, and use the native capability blocker. The Planner coordinates the permitted recovery path. Repairs outside the assignment require separate approval.
- **Verified quota/rate limit:** preserve the original message and known reset time or uncertainty. Use the established transient-block and authorized one-time resume/TIMER procedure. Do not bypass the limit or invent a reset time.
- **Repeated substantive review returns:** diagnose the cause under the existing retry/reasoning limits. The Planner coordinates a genuine impasse or required customer decision, not another routine technical review.

### 5.4 Triage and terminal failures

`Native circuit breaker / repeated block / terminal execution failure → established failure or triage event → Planner wake → inspect the recorded cause → coordinate authorized recovery or obtain missing approval → verify native return phase and assignment → dispatcher continues`.

Repeated legitimate customer pauses can still reach `triage`. Keep the existing recovery path; this proposal changes neither native block counters nor automatic decomposition settings. `triage` alone authorizes no task split, new scope, counter reset, or infrastructure repair. Restore review-phase work to review and implementation work to implementation as the native recovery contract requires.

## 6. Brief for the later independent plan review

Review this proposal before implementation. Check that:

1. Coder technical authority is explicit, bounded, and consistent across role and skill instructions.
2. A deliberate decision escalation means customer clarification, while recovery events remain distinct.
3. Review readiness does not become either a hidden full pre-review or blind trust in Codex.
4. Evidence reuse preserves attribution, valid inputs, independent checks, and explicit final-state acceptance.
5. Native handoffs, wakes, blocked/triage recovery, and correct return phases remain complete.
6. The proposed clarification-route change is consistent with deployed tool and subscription contracts.
7. No new gate, reporting store, dispatcher, role merger, or live rollout is introduced implicitly.

Report concrete contradictions, missing authority boundaries, and unhandled transitions. Distinguish policy review, Maker implementation verification, and live workflow evidence.
