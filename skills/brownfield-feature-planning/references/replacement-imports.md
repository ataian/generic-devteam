# Replacement-import planning

Use when externally supplied records create local aggregates and later imports replace them completely. This is a design and acceptance procedure, not a claim that an importer, migration or hard-delete path already works.

## Procedure

1. **Define the submission and identity contracts first.** Trace document origin → actual submitting actor → receiving endpoint → stored aggregate. Confirm whether an internal user forwards a file or an external system calls directly before choosing session/role authentication or machine credentials; reuse the applicable existing security boundary. Distinguish the external source key, the local aggregate ID, the stable visible number/name and nested object IDs. Ask whether the visible identity survives replacement; do not infer that deleting and recreating a row should renumber the person or resource. Establish whether source keys are global or source-scoped from the agreed sender contract, not merely from their UUID-like appearance. Completion: known submitting actor and access model, one unambiguous lookup key and an explicit identity policy across reimports.
2. **Establish an ownership boundary independent of the payload.** Resolve replacement targets only through the importer-owned mapping. Combine that provenance with the agreed expected local identity or namespace, and abort without mutation when they disagree. Never select a local deletion target from supplied object IDs, names, local business identifiers or a matching prefix alone. Keep the stable mapping and number outside the replaceable aggregate, with uniqueness and concurrency protection. Completion: a forged payload cannot nominate an internally created record, and inconsistent mappings fail closed.
3. **Trace export losses and the receiving read path separately.** Follow current export builders to understand projections, filters and omitted fields; then inspect entities, migrations and existing read APIs to identify technical storage and viewing requirements. When the sender uses a clone's exporter, use its existing field, purpose, version and code mappings as the first inverse-mapping specification; do not ask the owner to reconstruct the ETL for you. A many-to-one export mapping has no exact inverse, so explain the information loss and settle only the consequential remaining ambiguity. Ordinary create/edit DTOs may enforce authoring completeness that is inappropriate for external snapshots. Check nullability independently before proposing defaults. Inventory absent fields, supplied partial values and structurally inconsistent relationships separately. Do not silently discard supplied information or invent precision; obtain a representation policy only where needed. Once the owner explicitly allows normalization, encode and test the exact exception rather than continuing to treat it as forbidden fabrication. For partial dates, a permitted missing-day/month default must not invent a missing year or populate a wholly absent date. Do not infer positive consent or completed workflow states merely to make an incomplete record usable. Distinguish parsing, safe assignment and persistence from clinical completeness validation. Completion: each populated value has supplied or explicitly authorized provenance, each representation gap has a stated policy, and every rejected condition has a technical or agreed product reason.
4. **Remap imported identities as a document-local graph.** When external IDs need not be retained, allocate new local IDs and resolve references through a schema-aware map keyed by object kind and source ID. Inventory relational FKs, join tables, history/parent links and JSON/JSONB references, including nested findings and variants. Preserve clinical codes and external terminology identifiers; do not rewrite every UUID-looking string or use global string replacement. When target entities use ORM-generated IDs, distinguish new entity identity from nested JSON-object identity: obtain the actual managed entity IDs through the supported persistence path before finalizing reference strings, and test the save/merge behavior rather than assuming manually assigned generated IDs are accepted. Never fall back to looking up an unresolved imported reference in existing clinical data. Specify the agreed response to unresolved or ambiguous references before mutation. Completion: every supported relationship is mapped internally, and identical supplied IDs in different imports cannot collide with or attach to pre-existing records.
5. **Choose deletion by the required active-state outcome, then verify transaction semantics.** First distinguish complete snapshot replacement from physical erasure. If hard-delete is not a product requirement, prefer existing soft-delete behavior when it can fully remove obsolete content from active reads; do not add annotation bypasses, cleanup entities or purge infrastructure solely to implement an earlier deletion assumption. Inspect soft-delete annotations, global business-key uniqueness, incoming FKs, cycles, self-references and records without enforced FKs. A soft-deleted row can still occupy a global unique business key: consider preserving the stable aggregate identity row and replacing its entire mutable payload plus its active child snapshot instead of deleting/recreating that identity. Make this technical distinction explicit; an identity-preserving replacement must still clear every now-absent mutable field rather than use null-ignoring patch mapping. Load the complete old active child inventory before deactivating parents when repository queries traverse a parent soft-delete filter; otherwise subsequent queries can overlook children that still need deactivation. Deactivate obsolete clinical children themselves where deleting only their parent would leave them readable, and replace parent-scoped records such as consents too. Use ordinary repository deletion for owned records without soft-delete when appropriate. Preserve shared dictionaries and unrelated records. If physical erasure really is required, include historical soft-deleted owned rows and prove removal independently of ordinary filtered reads. Honor the agreed persistence abstraction; an existing native-query helper is not permission to violate a repository/JPA-only import contract. Keep ownership recheck, complete old-state deactivation, payload replacement, new snapshot creation and mapping update in one transaction on the actual target data source. Identify filesystem/external effects separately, since DB rollback does not undo them. Avoid authoring-service notifications, schedulers and outbound transfers. Do not add retention, purge or history-browsing features merely because old soft-deleted snapshots remain; keep unresolved retention policy outside scope. Completion: only the new snapshot is active, absent sections leave no stale current content, and failure restores the previously committed state without external effects.
6. **Define bounded tests before dividing phases.** Use synthetic data and an isolated target for mutating checks. Inspect how the existing integration harness constructs its database before treating it as faithful: verify migrations, views, foreign keys and sequences required by the acceptance path, not merely copied tables. A table-cloning fixture does not establish that a view-backed overview reads the same imported state. Prefer the smallest existing setup that preserves those semantics; if a dedicated migrated test database is needed, scope it to the feature instead of redesigning the shared test framework. Label that setup as planned until it has actually run. Include first import, replacement, rollback after deactivation, concurrency, forged-ID/ownership cases and existing read APIs. Make omission a first-class replacement test: import a record with a therapy or recommendation, then reimport the same source key without that group and verify it is absent from all relevant active reads, not merely associated with an older parent. Repeat for a previously populated scalar and parent-scoped consents. If using soft-delete, distinguish allowed archived rows from forbidden active leftovers; test physical row removal only when required. Test only the agreed viewing path; do not add a new frontend or lifecycle platform without a product requirement. Include schema migration, implementation and independent review in their actual repository boundaries. Completion: each assertion maps to required behavior or concrete changed-code risk, with no duplicate proof phase.

## Minimum acceptance matrix

| Scenario | Required observable result |
| --- | --- |
| First import | One mapping and one visible aggregate with the agreed generated identity; supported supplied data are readable. |
| Same external key again | Agreed identity remains stable; only the new snapshot is active. Historical soft-deleted rows are allowed when physical erasure is not required. |
| Later upload omits a previously populated group | Earlier therapies/findings/recommendations are no longer active or returned as current content; adding a newer parent alone is insufficient. |
| Later upload omits a prior scalar or consent group | Mutable scalar is cleared and prior current consents disappear; no null-ignoring update or old-data fallback. |
| Same nested IDs across different source records | Independent local IDs and relationships; no overwrite or cross-record attachment. |
| Payload contains an existing internal ID | No internally created record is replaced or referenced through that supplied ID. |
| Mapping points to an unexpected local identity | Atomic rejection; no deletion, reassignment or silent ownership repair. |
| Failure after old-state deactivation or payload clearing | Previous committed active aggregate, scalar values, consents and mapping remain intact after rollback. |
| Concurrent first/reimports | No duplicate mapping/visible identity, partial aggregate or unprotected interleaving. |
| Optional groups absent | Remaining data import successfully; no completeness rejection or placeholder clinical objects. Absent facts stay empty except for expressly agreed normalization rules. |
| Supplied date has only year/month precision | Apply the exact approved representation policy; where authorized, fill missing day/month with `01`, but never invent the year or populate a wholly absent date. |
| Duplicate IDs or unresolved relationships | Under agreed strict rejection, whole import fails and the prior snapshot remains unchanged; no silent skip or cross-record lookup. |

## Restoring previously accepted imports

Use this additional procedure when a reset or reassignment must undo processing of an already imported file, rather than accept a new external snapshot. These are discovery and design checks, not evidence that a reconstruction implementation has run.

1. **Inventory the actual mutation boundary.** Trace parser/mappers, processing helpers, repository saves and JSON converters. Build a small field-path table: imported value, processing mutation, persistence point, and available original source. Inspect nested setters as well as top-level assignments; changing an object returned by a getter and then saving its owning entity can persist content changes without calling the owner's setter. Distinguish a detached export-only working copy from a managed import record.
2. **State what the reset must restore.** Separate association removal, reversal of processing overrides and exact recovery of original imported values. If full technical reversal is required, do not substitute preserved effective values plus a promise that the next processing pass will repair them. Matching setter targets across processing modes supports a bounded reuse hypothesis, not proof of original-state restoration or future compatibility.
3. **Classify field ownership before choosing a recovery source.** An overwritten DB field cannot reveal its previous value or whether it was originally absent unless a raw snapshot/history was stored. If the required outcome preserves original source facts, use the retained original or an existing immutable snapshot when needed; a new snapshot column cannot recover already-lost legacy values. If the owner instead confirms that specified fields are processing-owned system values and accepts discarding their legacy values, reset that explicit leaf-field allowlist without source reconstruction or speculative age/version gates. State whether empty means null or an importer default such as false/empty string; these are not interchangeable. Preserve measurements and other siblings in nested objects, list order and entries outside the processing-owned positions. Compare the allowlist against actual processing setters, excluding setters that merely create parent containers. Separate identity allocation from source parsing: a need for fresh nested IDs alone does not require rereading the original file.
4. **Separate reconstruction from new-upload admission.** Inspect which existing importer checks are necessary for safe reading and relationship consistency, and which express today's allowed versions, mandatory content or completeness rules. A previously accepted source may fail newly tightened admission checks. Specify a bounded compatibility policy for restoration rather than blindly invoking the current upload/import method or disabling all validation. Keep structural readability, safe interpretation and atomic failure requirements. If the original format cannot be interpreted safely, report the unresolved compatibility boundary; do not claim that skipping validation makes it recoverable. Preserve normal new-upload validation unless its change is separately authorized.
5. **Test the selected restoration policy, not a superseded one.** For original-source reconstruction, include an overwritten populated source value, a processing-created nested object and a previously accepted fixture that fails current new-upload admission. For an approved system-field reset, instead assert the exact cleared allowlist, preserved measurement/sibling sentinel values and successful reset without source-file access; remove obsolete parser work and file/admission error responses from the plan. For either path, test changed processing configuration/type, null/empty nested data, protected historical objects and rollback after failure. Check shared mutable objects before clearing references, and snapshot old result IDs before any approved identity renewal, so resetting an import cannot mutate an archived report or resurrect removed references after reprocessing. Keep routine regressions synthetic; any additional real-source acceptance must follow the separately authorized local-data procedure below. Planned gates remain unverified until executed.

## Authorized local source-data acceptance

Use when the owner supplies a populated local test database or operational source files to exercise a realistic workflow. This supplements reproducible synthetic regression tests; permission to use the sources is not itself plan approval, implementation dispatch or evidence that the advertised baseline exists.

1. **Record the exact authorization and inspect metadata first.** Identify the supplied directory, local service/port, credential location and permitted purpose without copying credential values. Resolve ambiguous directory wording with a narrow parent-directory inventory; count allowed file types programmatically without printing identifying filenames or opening document content. Label each fact as owner-provided, metadata-verified, database-verified or execution-verified. A pair of files does not prove a matching imported record or successful historical job.
2. **Bind the scenario to actor and entrypoint.** If the owner mentions a blocked button while the feature provides a privileged exception, resolve that distinction before writing the acceptance expectation. Prove the existing ordinary restriction and the privileged success separately with the correct roles. Preserve the actual existing rule rather than inventing a universal prohibition from a status label; no new frontend control is implied by a test description.
3. **Establish the minimum baseline without widening access.** Inspect only necessary source fields and narrowly scoped database projections under the granted permission. Use neutral case aliases in plans, tickets and reports; retain their real identifier/filename mapping only in the authorized protected local context. Verify required associations and historical states rather than substituting assumed values. If missing prerequisites require synthetic setup, label that result synthetic instead of claiming to have exercised the supplied operational case.
4. **Choose the mutation target independently of source access.** Keep ordinary tests disposable and synthetic. For approved operational cases, preserve supplied originals and use a separately scoped local test target unless direct mutation of the populated database was expressly authorized. Take only the minimum authorized related data needed; do not turn a sample-file grant into a whole-database dump. Clarify genuinely unbounded data needs instead of silently copying unrelated records. Do not run automatic migrations, schema cleanup, volume deletion or scheduler startup against the source. Read credentials locally only when the next authorized operation needs them, never into tool output or shared artifacts.
5. **Define the finite postcondition and stop boundary before execution.** Describe the existing-flow sequence, such as restricted ordinary operation → privileged reset → permitted field change → normal confirmation with existing role/separation-of-duty rules → local reassignment/reprocessing. Distinguish these acceptance actions from new product features. Compare old/new active records, preserved source measurements, regenerated processing values, protected history and actual workflow state; do not mark all steps complete merely because reprocessing succeeded. If external submission is excluded, keep outbound clients/job execution disabled and prove no new submission jobs or external calls occurred through before/after job inventory and mock-call assertions. Do not submit even a test transmission to demonstrate readiness.
6. **Report only the evidence actually produced.** Keep source content and credentials out of Git, chat, task attachments, persistent memory and reusable fixtures. Use protected local work directories/files for necessary copies and clean only owned test resources. Report the exact code commit, neutral case alias, actual tested source/target mode, assertion results and gaps. Directory inventory, plan edits and a successful connection are not end-to-end acceptance. Retain independent review and the separate execution/publication gates.

## Schema-only confirmation on an authorized local database

Use this only when catalog evidence can resolve a storage/deletion question that source inspection leaves open. Inspect no patient rows and do not run an import or migration during planning.

1. Resolve the exact database service and target from the supplied local configuration. If using `docker compose -f <compose-file> config --format json`, capture and parse its output locally and emit only an explicit metadata allowlist; resolved configuration can contain secrets. Verify the Docker endpoint is the intended local target before querying.
2. Through `terminal`, use the existing database client inside that service rather than installing host dependencies merely for a catalog read: `docker compose -f <compose-file> exec -T -e 'PGOPTIONS=-c default_transaction_read_only=on' <db-service> psql -X -v ON_ERROR_STOP=1 -U <db-user> -d <database> -P pager=off`. Supply credentials only through the authorized mechanism, never echoed commands or reports.
3. Send `BEGIN READ ONLY; SET LOCAL statement_timeout = 10000;` followed by narrowly filtered `information_schema.columns` queries for nullability/types and `pg_constraint` queries using `pg_get_constraintdef(oid)` for incoming FKs, then `ROLLBACK;`. Read only required catalog definitions. Distinguish this evidence from importer execution, rollback testing or application-read verification.

## Documentation boundaries

Store concrete entity maps, table lists, source paths and confirmed defaults in the project's approved documentation location, not in this reusable skill. Keep original-source records and identifiers out of shared plans and evidence; pseudonymization does not make them publishable. Label technical recommendations as proposals until the applicable design gate is satisfied. A selected authentication approach is separate from provisioning real credentials or authorizing deployment.
