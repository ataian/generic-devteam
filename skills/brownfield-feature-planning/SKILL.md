# Brownfield feature planning

For evidence-backed project reviews, load [Bounded project retrospectives](references/project-retrospectives.md). Preserve original scope history and distinguish proposed process improvements from authorized execution.

## When to Use

Use when an existing application's feature brief requires discovery across current code, external reference data, and implementation phases. Use alongside the applicable brainstorming process; this skill supplies repository- and data-grounding, not permission to skip approval gates.

## Scope before discovery

1. State the requested executable outcome and its boundary before choosing a checklist. For an instruction-to-script request, read the actual agreed instructions and map each required step to inputs, an existing command/importer, affected resources and an observable result. If later documentation replaced those instructions with an expanded operating package, recover the agreed baseline with `git log -- <path>` and `git show <revision>:<path>`; use it to reconstruct the requested sequence, not to override the user's current requirements. Inspect only code and configuration needed for that path; a request to automate an import is not automatically a request to manage the application's operating lifecycle.
2. Reuse working commands and import logic behind the smallest executable interface. Accept the user's supplied data and target settings, perform the documented steps, and report success or a clear nonzero failure. Keep necessary validation, credential protection, data safety and recovery proportional to the actual mutations. Do not add activation, app upgrades, service control, rollback frameworks, source acquisition or configuration options unless the requested instructions or explicitly agreed functions require them.
3. Define a finite acceptance path for that executable: the documented invocation, a real safely isolated import and verification of resulting records, plus relevant failure and repeat-run checks. Do not make full-app images, simulators, authenticated UI, workflow-delivery proofs or a new test framework prerequisites for an import-only delivery. A missing fixture is bounded preparation work, not justification for expanding the product.
4. Resolve routine technical choices independently inside that boundary. When the user says the work has expanded beyond it, distinguish cancellation from narrowing: stop the superseded side work, not the still-requested delivery. Narrow the existing authoritative assignment, preserve reusable code and genuine safety constraints, park obsolete runnable successors and remove only dependencies belonging to the abandoned scope. If the remaining work is already authorized and its prerequisites are satisfied, release that existing assignment in the same interaction; do not leave everything blocked until the user asks again or request approval for another plan of the same goal. Verify the actual dispatcher claim before saying work is running. Explain the scope error and current delivered artifact briefly, not a long account of internal approval mechanics, and do not ask the User to manage ordinary tool use. Use [Scope narrowing without a delivery stall](references/kanban-status-inspection.md#narrow-scope-without-stopping-the-accepted-delivery) for the transition sequence.

5. Establish document storage and versioning together when plans must live outside the application repository. Check the agreed directory's Git ownership during planning, not only when tickets are ready. State any separate authorization needed for an external versioned baseline without blocking the specification itself. Do not initialize an extra repository, commit documents into a sibling repository or treat a checksum as a Git commit merely to satisfy the later handoff gate.

Apply the deeper sections and references only to requirements actually present in the accepted scope; their existence is not authorization to add those requirements. When the User explicitly rejects a plan or withholds approval, answer the concrete operator-contract questions briefly and keep that plan unreleased; neither an earlier broad approval nor a new technical suggestion authorizes its tickets. Label existing behavior, proposed behavior and actually verified behavior separately.

## External-data discovery and scope

- Preserve the requested purpose before treating an import as an inverse export: an incomplete external record intended for viewing is not a backup restore. Do not turn irreversible mappings or absent local authoring fields into new completeness requirements, editing locks or frontend work without an agreed product need.
- Establish who actually submits a document before proposing authentication. External file origin does not imply a machine-to-machine integration: an internal user upload should reuse the existing session and role checks unless the owner requests another access model. Distinguish the requested user-facing role from its verified backend authority token; do not create or silently substitute identity roles.
- For clinical snapshot imports, keep missing facts absent; do not fabricate case/insurance identifiers, consent decisions, completed workflow states or unapproved date components to satisfy authoring DTOs. Separate generated technical identity from clinical facts. Inspect storage and read-contract precision before choosing a representation policy. If the User expressly permits date normalization, apply that exact rule consistently, such as filling a missing day and then a missing month with `01` while leaving an entirely absent date empty; do not keep proposing precision archives or rejecting permitted partial dates after that decision. Keep any unapproved preservation proposal labeled as such.
- Distinguish permitted incompleteness from inconsistent input. When strict rejection is agreed, reject contradictory IDs and unresolved relationships atomically, retain the previous snapshot and never report partial import as success; optional absent groups are not grounds for rejection.
- Treat pseudonymized clinical material as sensitive, not synthetic. Inspect large supplied JSON machine-side and return only required schema-known field names, types and collection sizes; never dump values, arbitrary dictionary keys, embedded free text or source filenames containing identifiers into chat, delegates, plans, tickets or fixtures. Compare actual input shapes with current builder contracts, because historical documents can differ in field naming or multiplicity. Use synthetic fixtures for shareable evidence. Record an owner-provided populated database or operational-file collection as a scoped local test resource, not proof of connectivity, matching imports or permission to reset the source. Distinguish permission to use particular files from permission to mutate a database, export records or start implementation; retain only non-secret resource locations and neutral case aliases in shared planning artifacts. For the bounded acceptance procedure, use [Authorized local source-data acceptance](references/replacement-imports.md#authorized-local-source-data-acceptance).
- Keep a requested export explanation compact: trace the active runtime builder, then document DB table → target object path and only consequential filters, identity substitutions or losses. When incoming documents come from a clone's exporter, derive routine inverse mappings from that ETL before asking domain questions; do not ask the User to re-specify mappings already established in code. Explain genuinely irreversible many-to-one mappings once, obtain any necessary semantic decision and reuse it without reopening the same issue. Distinguish source-derived behavior from runtime verification; do not let mapping documentation become another implementation phase.
- Before planning a reset of imported data, trace source parsing → persisted import → processing → downstream export, including nested JSON mutations and explicit saves/ORM dirty checking. Do not assume an import table is immutable. Distinguish restoring the original imported state from merely making processed data reusable: retaining overrides because a later processing pass may overwrite them is not a complete rollback. Separate reconstruction of previously accepted source data from admission of a new upload under today's validation rules; changed mandatory fields or supported versions must not silently redefine the reset contract. Use [Replacement-import planning](references/replacement-imports.md#restoring-previously-accepted-imports) for the mutation inventory, compatibility decision and acceptance cases; treat any unimplemented reconstruction path as a proposal, not a verified solution.
- When the product owner confirms that processing-owned fields are derived system values rather than source facts, prefer an explicit leaf-field reset over mandatory source reconstruction. Record the policy for legacy values instead of adding speculative age/version gates; preserve measurements and other siblings in nested objects, distinguish null from parser defaults, and prove the reset allowlist against the actual processing setters. Deep-copy data shared with historical records before clearing associations or renewing technical identities. Remove superseded reimport work consistently from phases, file lists, API errors and acceptance tests; the clarification does not itself approve execution.
- For replace-on-reimport features, define the observable replacement contract before choosing hard- or soft-delete: a complete snapshot means all currently supplied content replaces the old content, not that every clinical section must be present. A section omitted from a later upload must disappear from the active read model, and omitted fields must not retain prior values. Settle stable identity and importer ownership separately from row recreation. If soft-delete satisfies the agreed outcome, do not build hard-delete bypass infrastructure merely to preserve an earlier technical proposal. Honor an explicitly required controller → service → repository boundary even when existing repositories contain tempting native-SQL helpers. Follow [Replacement-import planning](references/replacement-imports.md) for deletion choices, reference remapping, atomicity and omission-focused acceptance checks.

## Repository discovery and phased planning

1. Read the feature brief and inspect the relevant interaction at its actual call site: UI widget and bound state when applicable, persistence/output path, relevant API boundary, tests, and recent repository state. Trace any input-length limit, normalization, truncation, and downstream match semantics before promising that a catalog selection searches for an exact identifier; a displayed full code can silently become a shorter prefix in the actual query. When distinct full codes collapse to the same effective input fragment, show both the selected-code count and the distinct-fragment count before batch-add, because otherwise the user expects more independent query terms than the application will send. Distinguish active code from commented or removed UI and old plans; otherwise a design can target a flow users no longer reach.
2. Read the supplied data *and its accompanying schema/readme* before proposing a lookup, import, or validation rule. Confirm encoding independently for each file, delimiter, field meanings, multiplicity, version, and whether the source covers every valid identifier. A descriptive or synonym-rich catalog may omit valid codes, so never silently make its search results an allowlist. For longitudinal data, distinguish a current annual snapshot from a historical union: check whether retired identifiers remain searchable, and ask whether coverage means identifiers actually present in the user's records or every identifier ever issued. Do not promise historical completeness from the latest edition; if old labels are required, identify a historical source rather than inferring them from current titles. Locate supplied bulk inputs from maintained import documentation before searching the whole home directory; narrow filename searches to their documented location. Recheck canonical files and hashes because temporary mock copies may share the real catalog’s filenames. Put paths/provenance in the existing handoff only when disclosure is permitted; sensitive filenames can themselves contain patient identifiers, so retain restricted source identity only in its authorized local context. If bulk source files must stay outside Git, include an explicit repeatable, atomic importer in the feature scope; version its schema, small tests, and a terse instruction with real import and verification commands, because a database-backed search without a reproducible load path is incomplete. Keep import opt-in rather than coupling a mostly static bulk load to ordinary application startup.
3. Reflect the user's intended outcome and separate observed behavior from assumptions. Ask one consequential domain question at a time, prioritizing whether lookup is optional assistance or authoritative validation, and how multi-code records map to the existing input. Do not decide either from the dataset shape alone. When a test narrative says a control should be blocked but the feature deliberately introduces a privileged exception, clarify whether the owner means the existing ordinary UI/service path or the new privileged endpoint before changing requirements. Bind the resulting acceptance checks to actor, entrypoint and persisted state; a disabled control alone is not server-side enforcement, and an ambiguous button name does not authorize new UI work. Resolve technical implementation details independently within the accepted goal; ask the User about changed use cases or materially changed agreed functions, not to choose routine engineering details. Keep explicit plan-amendment approval separate: deciding a technical approach does not authorize an additional coding phase outside the accepted scope.
4. Compare the smallest viable integration approaches against the existing frontend/backend boundary and constrained clients. Specify server-side bounded results, request timing, response size, failures, and unchanged manual-input behavior when relevant; avoid shipping the whole catalog to the browser merely because it fits on the server. For many-to-many catalog hits, distinguish individually *selectable* codes from individually *submitted* codes: offer checkboxes with one batch-add action, keep selections across server-side filtering and pagination, count selected items, and label page-only select-all explicitly so broad matches cannot be silently added en masse. If the user prefers unobtrusive failure states, distinguish intentional disablement (hide control) from temporary unavailability (disabled control with tooltip), preserving the manual path without a prominent warning. When an optional feature uses a separate datastore, trace how environment variables reach each process and define one authoritative enable flag: disabled means no datastore, connection attempt, migration, import, or dependent UI is required, while the original workflow still works. Explicitly choose the default flag value so existing installations cannot accidentally become dependent on the new datastore. Decide separately what happens when enabled but the datastore fails: keep the core app running if the feature is optional, expose a lightweight unavailable status, log the cause for operators, and allow recovery without an application restart; otherwise a helper feature can take down the main workflow. Distinguish a per-database dump from a whole-cluster or volume backup before claiming datastore separation removes backup load.
5. Identify the actual repository boundary for each change before dividing phases. Before a coding-harness handoff, verify the required project- and module-rule files and pass their absolute paths into the worker prompt; distinguish the project root from the user home and the Git root, because ambiguous “root/module AGENTS.md” discovery can turn an unrelated optional ancestor file into a false prerequisite. Do not create placeholder rule files or suppress genuine read errors to make discovery pass. In separately versioned repos, order producer artifacts before consumers (e.g. shared contract install → backend → frontend) and make local build/install prerequisites explicit, because a later phase otherwise may not resolve the dependency it assumes. Give each phase one demonstrable acceptance gate, one repo-specific commit boundary, and an ordered dependency. Inventory existing callable repository methods before declaring new persistence work; classify planned files as new, modified or reused and verify those classifications against the current tree, because an already available query needs reuse rather than another API or speculative repository edit. Resolve abbreviated paths against the explicitly declared production, test and generated-source roots when checking the file matrix; a test class checked under the production root creates a false missing-file finding. Map every gate to the files and repository changes needed to satisfy it before approval; a gate spanning independently versioned repositories needs explicit reviewed prerequisites in each repository, because one repo's configuration cannot protect its sibling. Reserve tickets until the user explicitly accepts the whole plan. If a dispatched worker exposes an accepted gate/scope contradiction, preserve the safety gate, propose the smallest repo-specific prerequisite with its own commit and review, and obtain explicit approval of the plan amendment before creating or releasing additional coding work; do not silently widen the workspace or substitute an unversioned workaround. Distinguish creating deployment artifacts from applying them before asking for a target host. When the user requests only scripts, documentation or a plan, state that live deployment is out of scope and do not make host selection a prerequisite; name an isolated verification environment instead. Ask for a host when actually planning application to a deployment. When a supplied proposal cites an older branch but the User designates the currently checked-out branch as the planning baseline, verify `git branch --show-current`, `git rev-parse HEAD` and `git status --short` in the canonical repository before analysis; do not switch branches or merge merely to match the proposal. Complete any required graph-index synchronization before structural analysis, then verify the stored graph branch/head against that Git baseline. Use `git diff --stat <proposal-commit> HEAD -- <relevant-paths>` to bound the changed areas, and re-read material definitions and callers before reusing old line citations. Record the proposal reference commit, current code baseline and later approved-plan commit as three distinct identities. Before proposing an application-version bump or a version-policy exception, inspect the current version sources and relevant Git history for a step already completed on that baseline. When the User confirms that the branch already contains the intended new version and the sources agree, record the version prerequisite as fulfilled rather than demanding another bump or inventing an exception gate; do not infer completion from one matching tag alone. If the user updates the baseline during approval, repeat the affected checks and carry the corrected baseline into the accepted plan and every ticket; do not preserve stale findings or infer that matching version tags prove matching artifacts. Put genuinely unresolved data-source decisions in the plan as questions, not implied defaults.
6. When the accepted plan enters a multi-agent Kanban pipeline, explain the board sequence before writing if the user wants to inspect it. Read-only preflight: list boards and choose the team board by explicit slug rather than trusting the current-board pointer; verify dispatcher/review routing, worker and reviewer profiles, and a one-active-task-per-profile limit. Persist plans, amendments, decisions, operator handoffs and verification reports outside module-owned repository documentation in the agreed top-level `docs/<feature-name>/` collection, not only a role profile, scratch directory or board. Write the central file first, then link or attach a snapshot in the board. Use dated phase/range-specific filenames and a README index; distinguish current instructions from historical snapshots, and make each handoff understandable without board access. During migration, inventory both profile files and board-only earlier document versions, preserve active ticket paths, synchronize still-referenced working copies, and record source/hash provenance for unchanged copies. Do not relabel historical dispatcher-release checks as product acceptance. Leave existing module-owned product documentation in its repository and link to it centrally. Check index links and collected counts; explicitly separate board-independent storage from backup or Git versioning, and do not initialize an unversioned parent directory or commit its documents in a sibling module merely to satisfy an archive request. Reference the durable path in each body and attach the same accepted document to each ticket when a snapshot is required. Read existing attachments first and reuse a verified identical snapshot; repeated uploads can create renamed duplicates, so verify the returned attachment ID and stored filename rather than assuming the requested basename identifies the new file. Create every phase ticket initially blocked, with a retry-safe idempotency key, repo-specific workspace, acceptance gate, commit boundary, and explicit reviewer handoff instruction. Record each returned task ID immediately in a durable manifest. Only after all tickets exist, link the full parent chain and read back every task's status, assignee, workspace, reviewer instruction, parent/child edges and required notification subscription. Use bounded per-task reads for verification rather than parsing a potentially truncated whole-board dump. If verification fails after a successful write, recover by reading the recorded exact targets; do not repeat creation or release merely because the output parser failed. Release descendants in reverse order and the first phase last: otherwise a dispatcher beat may claim phase one before the rest of the graph is ready. Read back the board once more; phase one alone should be ready or running, while descendants remain parent-gated. Never manually dispatch or start follow-up work when the agreed process leaves those decisions to the dispatcher and human acceptance.
7. If a dispatched worker crashes, inspect the exact task state, run history, worker log, and dispatcher diagnostics before acting; a notification saying “will retry” can be superseded by a later failure-limit block. Distinguish a pre-agent launcher failure from an implementation failure by tracing the parent process command, child argv, interpreter, working directory, and module resolution. Keep the task blocked while unresolved, so its descendants remain gated. For an operator handoff, write a durable file with observed evidence, a narrowly scoped candidate repair, restart impact, a non-secret verification check, rollback, and the exact condition for unblocking. Do not call a launcher version check an end-to-end fix: verify that the real worker advances past startup after the operator changes the runtime. Then distinguish worker startup from the coding harness actually accepting a harmless request; a heartbeat proves only the first boundary. If a reviewer worker exits mid-review, check whether the board preserved `review` provenance and already spawned a retry before intervening; truncated natural-language output is not evidence of a code defect or a completed verdict. Leave an active retry alone and report implementation, review, and downstream-gate states separately. If the coding CLI rejects its mandated model, inspect the worker's model policy and account type before proposing a retry; changing models may require an owner decision, not a silent fallback. Check the coding harness's actual outcome, not just its outer process exit: an exit-zero wrapper can contain an inner command failure and explicit STOP. Require the named artifacts, verification results, scoped commit and reviewer handoff before reporting completion. If the harness aborts, inspect Git HEAD, the working tree, the exact missing deliverables and targeted writer-process state before deciding how to resume; a tool timeout proves neither a security denial nor child-process termination. Preserve completed commits and partial changes. When only a handoff document or final summary is missing, explicitly exclude reimplementation and duplicate commits from the existing card's remaining-work instruction. Check that the prior writer has ended before authorizing another writer, and require a suitably tracked execution lifecycle without changing approval policy. Treat generated evidence documents as provisional until their acceptance checks are verified against real execution; an interrupted run can leave both implementation and success-looking reports without a completed gate. Report a released or newly claimed continuation as such, never as proof that the timeout repair or missing deliverable succeeded. When the new failure concerns an ambiguous instruction rather than the already-fulfilled coordination prerequisite, clarify the existing authoritative task body and central handoff instead of rebuilding the proof graph. Keep the mandated STOP/no-fallback policy intact, distinguish authorized resumption from a verified repair, and re-check ownership and downstream gates before release. Record the resumption conditions on the existing ticket and read the comment back; do not recreate the task or confuse retry authorization with proof that provider capacity has recovered. Investigate token/401 errors as a separate boundary, and check authentication in the worker's actual home/config context rather than trusting a login-status command from the planner's shell. Keep the phase blocked and descendants gated until the operator verifies the harness path. A planner documents and routes infrastructure repair rather than silently changing the shared gateway or coding profile. Treat a headless command-approval denial as a capability boundary, not provider capacity or bad credentials. Preserve uncommitted work and dependency gates; do not bypass denied access or actions, and do not globally loosen approval policy. Rejection of an unsuitable command form does not forbid an otherwise authorized read with an available native read tool. Explain an approval block by naming the stopped execution boundary and the concrete operator action that resolves it; do not ask for credentials again when access is already verified, or imply another chat approval changes a headless runtime policy. Provide an operator handoff for an explicitly approved interactive acquisition or pre-provisioned artifacts. When the operator reports completion, inspect the current board and independently verify artifact identities in the intended execution engine. Check separately that the next assigned execution context can perform its remaining required operations; successful provisioning in another session does not establish that capability. Preserve the partial diff, archive the operator result and independent verification centrally, and read back the existing task's gate comment and attachment. Unblock only when all conditions needed for that task's next supported step are satisfied, then verify its successor remains dependency-gated; resolving an artifact prerequisite alone must not redispatch a worker with an unresolved approval boundary. Leave dispatch, implementation and review to their assigned roles. Accessible registry metadata and permission to pull are not evidence that acquisition executed. Separate successful operator provisioning from the actual worker's command-approval capability: content-level guards may reject even local inspection of approved private-registry images. Do not carry approval evidence across profiles or sessions; inspect the real guard's persistence scope. If a retried task reaches triage, preserve that state and provide an operator handoff covering the full verification context plus safe task ownership/review routing, rather than repeating provisioning or blindly releasing another headless attempt. Re-read triage tasks immediately before any transition: an automatic decomposer can concurrently add duplicate children, change the root's parents and start a worker. Inspect those actual cards before intervening, stop an unauthorized active worker through the supported claim/reclaim mechanism, park runnable duplicates and verify their process/run state, preserve provisional diffs, and keep pending descendants dependency-gated. Do not delete new parent edges if that would immediately redispatch the unresolved root; route graph reconciliation and automatic-triage policy to the operator, correcting stale status notes in the durable handoff.
8. Treat Kanban notifications in a subscribed chat as automatically delivered board events, not as text the human necessarily typed: ticket creation can auto-subscribe the session, and the desktop gateway can submit an event as a synthetic conversation turn. Explain that distinction when asked how progress arrives; the event stream does not imply the planner reads worker logs continuously or receives an aggregate “all phases done” hook. On a phase-completion notification, read back the exact task and the whole board rather than treating the notification as proof of the dependency transition. Check the independent reviewer verdict, commit and test evidence, any bounded caveats, and that only the immediate successor became ready while later phases remain gated; do not manually release or dispatch the successor. If Maven warns that `-P` names a missing profile, determine whether the profile is supplied by the user's external `~/.m2/settings.xml` rather than the project POM; a successful build may use POM defaults and does not prove DB credentials or connectivity. Check the actual property values without exposing secrets before classifying the warning as a code defect or treating a DB-dependent command as validated. When the user asks to defer an independent documentation follow-up, create small repo-specific tickets with commit and reviewer gates in a parent chain, initially blocked; read back the chain and leave every ticket blocked until the user explicitly releases it, because a `ready` ticket can be claimed immediately by the dispatcher.

## Revising an existing plan after a skill or rule change

1. Read the current plan, accepted specification, repository rules and replacement skill with its relevant references before editing. Classify each supposed exception by its actual source: obsolete skill default, explicit product decision, approved repository-rule exception or accepted visual deviation. Remove only superseded defaults; a replacement skill cannot waive repository rules or cancel approved scope.
2. Update the existing plan in place when product intent is unchanged; leave the accepted specification and rule files untouched. Reuse documented decisions rather than restarting a requirements interview. Present the revised plan for explicit acceptance before creating or releasing implementation tickets; a request to revise is not execution approval.
3. Keep the plan lean by placing common constraints, checks and handoff rules once, followed by each phase's files, interfaces, dependency, concrete tests, acceptance gate and commit boundary. Replace long historical preflight transcripts with a short attributed evidence summary and the conditions for refreshing it. Do not repeat obsolete override warnings in every phase.
4. Preserve independently reviewable phase boundaries and safety gates; merge phases only when the combined deliverable still has a coherent test/review boundary. Keep approved runtime budgets unless evidence or a new owner decision supports changing them: shorter prose does not prove cheaper implementation. Label project-specific render budgets as agreed limits, not universal rules supplied by a skill.
5. Self-review against every specification section and compare the old/new phase, gate and commit counts. Check the focused documentation diff with `terminal(command="git diff --check", workdir=<repo>)`; calculate any advertised size reduction from the actual old/new files. Report separately what became shorter and what scope or effort remains unchanged. Commit only the intended documentation and provide the actual revised document for review, not merely a summary of changes.

## Time and cost discipline

1. Preserve the user's cost-control requirements when shortening a plan. State target effort separately from hard per-run timeouts, retry/fix allowances and the estimated elapsed delivery window; reducing document length is not evidence that implementation became faster.
2. Calculate estimates from the actual phase table with a tool. Include independent review in a sequential pipeline and state whether dispatcher waits, provider delays and correction rounds are included. Never describe summed per-attempt limits as a global completion or monetary cap; fresh attempts and review runs can consume additional time.
3. Make stop rules executable and explicit: what happens near the phase limit, which additional calls or correction rounds are allowed, and who may authorize more budget. At budget exhaustion preserve partial work and report the missing gate instead of weakening acceptance criteria or silently continuing.
4. On explicit plan acceptance, carry these rules into each card and read back the native limits before release. Use the verified CLI if required fields are absent from the available tool schema; do not replace an enforced limit with prose or invent database writes. For the staged creation, attachment verification and release procedure, load [Kanban phase release](references/kanban-phase-release.md).

## Verify the plan artifact before an authorized documentation commit

1. Check phase numbering/dependencies, required per-phase gates and acceptance-case identifiers against the actual written document; compare the file matrix with the correct source roots and distinguish proposed files from existing ones. Treat a validator's path-resolution error as a checker defect to correct, not evidence that the plan's files exist or are missing.
2. Run document validation in a separate read-only tool call, inspect its complete result, and proceed to staging only after it passes. If combining commands, connect validation to every write with fail-closed control flow (`&&` or an explicit checked exit); a newline before `git add` does not stop a shell after a failed Python assertion, and a successful final commit can mask that failure.
3. When the applicable assignment authorizes a documentation commit, inspect the current staged and unstaged changes, stage only the intended planning files, and run `git diff --cached --check`. Verify the resulting commit's changed-file list, parent baseline and working-tree state before reporting completion. If a commit already occurred before a checker failure was noticed, inspect that exact commit and rerun the corrected checks; do not create a duplicate commit or rewrite history merely to repair the verification narrative.
4. Report document validation separately from application verification. A checked and committed development plan does not establish that its proposed lock, migration, parser or rollback design has run successfully; keep those implementation tests as future acceptance gates and do not retain the unapproved design as a proven reusable solution.

## Kanban status checks and evidence reporting

1. Inspect the exact notified task and its run/event provenance before responding. A review worker can appear as `running`; identify its role from the claimed run's `profile` and review origin rather than reporting that implementation restarted. Read the latest implementer `review_requested` handoff separately from the latest reviewer run, because a newly claimed review row can have an empty summary.
2. Use structured `kanban_show`/`kanban_list` for ordinary board reads and `read_file` for saved JSON, reports and spillover text. Do not introduce `execute_code`, Python parsing or a scratch export merely to read, select a few fields or acknowledge a task: that creates a code-execution approval boundary where ordinary read tools suffice. If native output is persisted because of size, page the existing result with `read_file` rather than re-fetching it or creating an execution dependency. Reserve authorized scripted extraction for a genuinely substantial machine-validated batch that native tools cannot supply; an approval failure does not authorize denied access or actions; use native read tools for otherwise permitted reads. Keep inter-agent assignments, questions and results on the existing Kanban card, with durable report links in the agreed project documentation. Treat profile scratch JSON as the creating session's private parsing aid, never a required handoff path; put missing handoff content on the card or in the durable report rather than asking the User to authorize another agent's scratch access. When using CLI JSON, parse and reduce the complete output inside the executing process before returning it through a bounded tool-output channel; truncation can turn valid JSON into a decoder error. Inspect the returned schema before writing assertions: native tool responses and CLI JSON can expose different fields. Treat omitted claim or parent-satisfaction metadata as unknown, not safe-looking empty defaults; resolve it through exact parent reads, run provenance or a native read. Re-fetch the same targets after a read/parse failure; never recreate or release tasks to repair an output problem. For a reusable extraction recipe, load [Kanban status inspection](references/kanban-status-inspection.md). If the terminal wrapper truncates native CLI JSON before Python can parse it, redirect the CLI's stdout to a private file in the active profile's scratch directory, parse the complete file and return only bounded verified fields. Do not relax the JSON parser, reconstruct missing content or repeat a state-changing operation to repair a read failure; re-read the exact already-written target. Persist multi-task verification batches and compare the collected IDs/counts with the intended set before release.
3. Report the current phase state, attributed test evidence, consequential caveats and immediate successor state briefly. When the User questions an approval prompt, identify the exact attempted operation and guard evidence before explaining its cause; distinguish file-access restrictions from approval of code execution, and label the cause unknown when the concrete prompt or trace is unavailable. Remove an unnecessary handoff prerequisite through the existing card, but do not bypass denied access or actions or claim that a likely guard mechanism is the verified reason. An unsuitable command form alone does not bar an otherwise permitted native read. When the User asks whether work is finished or why it is silent, answer that first; distinguish active execution from idle dependency waiting and name the last actual deliverable, the next responsible role and any owner decision genuinely required. Do not present a posted clarification or acknowledgment as resumed execution. Before relying on an asynchronous handoff, verify that its actual event kind is covered by the installed notification/wake policy and that the existing next card can advance; a subscription alone does not guarantee a coordinator turn for every state transition. Keep any unsupported handoff explicit rather than promising automatic progress, and do not create new watchers or runtime changes without authorization. Say `ready` when the dispatcher has not claimed the successor; reserve `running` for a verified claim. An implementer's green tests are not reviewer approval, and an approved phase is not acceptance of the whole package. If the independent reviewer actually executes a previously missing check, resolve that specific verification gap with the reviewer's provenance; do not retroactively claim the implementer ran an earlier denied check. Preserve pre-review reports as historical observations and add the actual reviewed completion, commit and bounded successor state to the central feature collection and its index, because board-only verdicts are not long-term documentation. Do not manually advance an intact dependency chain.
4. When the final implementation differs from the tree used for the full acceptance run, carry the missing exact-head check into the existing reviewer handoff. Resolve the caveat only after the reviewer records that full run on the final commit; targeted tests alone do not establish the integrated gate.
5. On a planner escalation or operator-result notification, read the existing decision card and its active run before proposing another workflow. If its acknowledgment worker is already running, deliver the current chat's actual receipt and report assessment through that card: write a separate central receipt record, post its link and verified provenance, and read the comment back. Leave that worker's decision report, run identity and completion to its owner; sharing a profile name does not confer ownership of another session's claim. Distinguish acceptance of the bounded operator report from completion of the proof phase and from product release. After its acknowledgment owner completes, verify the actual boundary repair and process end before resuming the original blocked card: board `done` can precede worker exit and final report edits. Preserve the original task and all valid parents; give its next worker an explicit remaining-work instruction so completed coordination probes are not recreated. Release only that existing card through the authorized native orchestrator tool, then read back its new run/profile and the still-gated descendants. Never reuse an old run identity or treat acknowledgment completion as coding/review acceptance. Coordinate through the existing card rather than starting duplicate planning or closing another session's claimed work. Reconcile overlapping proposals into one explicit authoritative amendment, including exact file scope, commit boundary, gate and dependency order; mark superseded proposals clearly, because parallel sessions otherwise leave the user approving different variants. Treat a subsequent needs-input notification as the same pending decision, not new approval or a reason to recreate tickets. After explicit amendment approval, insert only the new reviewed prerequisite into the existing graph: keep the successor blocked while creating and binding the prerequisite, preserve still-valid parent edges, attach the amended plan to both tasks, and verify exact parent sets, notification routing and snapshot contents before release. Return the successor to dependency-gated todo before releasing the prerequisite, then read back both states; otherwise the dispatcher can claim a successor before its new gate exists.

## Decisions on operator-executed verification

Use when a proposed amendment separates product development from approval-requiring verification. This is a decision and handoff procedure, not a claim that a native worker pause/resume mechanism exists.

1. Read the complete supplied proposal, the current authoritative plan, the exact task/parents/runs and the relevant working-tree state before deciding. Attribute approval to the current user message rather than treating a proposal's status line as independent authorization; distinguish conditional support, accepted responsibility changes and concrete runtime approvals.
2. Give a direct decision first: accept the bounded operator route or name the necessary changes. Explain why briefly. Separate agreement to the approach from operational release; an accepted responsibility amendment does not prove a working transition between implementation, operator execution and review.
3. Preserve the fixed role split of your team as defined in your SOUL:Your Coder (via Codex) owns product changes, test specifications, result assessment and commits. Limit her coordination prerequisites to understanding her own task, relevant parent handoffs, repository safety and her own review handoff; assign whole-board monitoring, notification delivery, subscription setup and dependency-release verification to yourself/the authorized orchestrator. Your Reviewer owns independent review and specifies and assesses his own rechecks. You coordinate rather than executing lifecycle tests. Label operator output as operator evidence, never evidence that another profile's worker performed or could approve those operations. Limit the amendment to its named phase; do not inherit it into successors.
4. Record the amendment centrally first, then update the existing authoritative task body and every still-referenced active plan copy. State exactly which previous responsibility instruction it supersedes and which gates remain unchanged; preserve original proposals and handoffs as historical evidence. A comment alone must not leave the next worker reading a contradictory task body. Read back the exact task to verify the amended body, comment, unchanged status, parent set and run state.
5. Keep operational release gated on a demonstrated supported task-bound transition, safe reconciliation of unwanted auto-tasks and a verified delivery/acknowledgment path to yourself. A posted comment is not confirmed receipt. Do not invent claim/pause/resume support, reuse historical run identity, create a parallel worker, mark redundant work falsely done, remove protective parents or use repeated capability blocks as a waiting mechanism. Keep central infrastructure changes and new monitoring jobs outside this amendment unless separately authorized.
6. Require reproducible test orders, frozen source identity and actual execution evidence. Repeat the required regression and real lifecycle checks on the final commit; prior pre-commit checks do not satisfy that gate. Have your Reviewer choose and assess independent rechecks. Preserve security and isolation gates and stop at denied access or actions; an unsuitable command form alone does not bar an otherwise permitted native read. Release the successor only after regular independent reviewed/done of its prerequisite.

### Check necessity and role scope before proposing infrastructure

1. Anchor each intervention to the next unfulfilled deliverable of the accepted project. The User expects completion, not an expanding investigation: inspect the exact task, latest failure, relevant repository state and immediate dependencies first; deepen inspection only when it can change the next safe action. Report the correction, verified progress and remaining acceptance gate briefly rather than recounting the diagnostic history.
2. Before expanding an approval failure into runner/gateway development, determine whether the denied operation is required for that deliverable and belongs to that worker. Keep coding, native own-task handoff, coordinator board/routing checks and operator execution separate; do not make a coder audit the entire board before ordinary development. Reassigning the same headless operation to another agent is not a capability repair.
3. When the owner stops or narrows an overbroad phase, inspect the current exact card and run before acting; a queued block notification may describe work already stopped. Replace contradictory active body instructions with the current scope/hold through the supported edit command, explicitly supersede historical attachments and read back body, status and run. A stop comment beneath an active execution order is insufficient because a later worker can follow the obsolete body. Preserve historical denials, useful code and genuine product gates; do not release the task, create replacement probes or seek the abandoned workflow's permissions merely because a delayed notification arrived. Remove an unnecessary operation entirely, never rephrase or reroute it to evade a guard.
4. Resume only the smallest remaining authorized work on the existing card. Permit a frozen implementation commit to precede externally executed acceptance when the accepted workflow requires it, but never count that commit as final verification or reviewed completion. Keep execution repair within the accepted scope; propose new infrastructure or phases only when a required product gate actually demands them.

### Native dependency handoffs before new runner/core work

Before proposing capability repair, inspect the exact task body with `kanban_show`, the original worker log and the denied operation. Map each requested check to an accepted deliverable and its responsible role; distinguish a required outcome from the worker's chosen command syntax. Separate ordinary repository preflight, orchestration evidence and genuine operator execution before enlarging the solution. ## Operator-package planning

Name repositories/modules, Compose services, images and host-side deployment paths explicitly. Do not use “the module” or “Docker module” as a substitute for an exact repository name, and do not conflate a source repository with a running container. Before proposing phases, explain the execution chain in operator terms: exact host-side script path → compiled command and its producing module/image → process or container running it → target database. Clarify whether a temporary container runs only a utility or a second application instance, because reusing an application image does not imply starting its server. State whether each component already exists, is proposed or has been execution-verified.

1. Establish the operator-runtime contract before selecting a language or copying developer instructions. For Docker-only production deployments, require only Docker and ordinary shell facilities on the host: no Java, Maven, Python installation, source checkout or build step. Place the operator entrypoint and its short README in the deployment/Docker repository, not the backend source repository. Reuse existing import logic through an already-built artifact with its required runtime inside a container; verify the executable, dependencies and input/network path before presenting that approach as working. Keep business logic in its producing module and make the deployment-repository wrapper invoke the packaged command; do not replace that boundary with copied backend sources, host compilation or a second parser. Inspect the existing application image before proposing a separate tool image. Explain running-container execution versus a bounded temporary job as a resource-isolation choice, not a functional necessity; an additional process shares the running container's memory limits, while a temporary job must explicitly bypass the application server entrypoint. Moving a script while retaining backend-source paths or host compilation does not make it a deployment tool. Inspect only the maintained instruction, relevant executable and deployment wiring needed for the accepted outcome; do not turn import automation into application-lifecycle management.
2. Show the complete operator journey before proposing phases: the exact configuration file and keys supplying DB credentials, what the operator must enter, the single normal invocation, the changed resources and the result. Verify names and file-to-process wiring; do not assert that an existing dotenv file has particular credentials without evidence, or describe a proposed configuration reader as implemented. Keep the README short and command-first: necessary setup, one copyable invocation, success/failure and the genuine activation prerequisite. Leave architecture, test-isolation terminology, historical workflows, speculative cases and irrelevant password-rotation discussion out of the normal path; retain necessary safety behavior in the implementation and link optional technical depth separately. Make the executable own required container access, authentication and verification. Keep existing passwords and unrelated service/data state unchanged unless explicitly required and authorized. Distinguish importing data from enabling the application: current images alone do not prove the feature flag and connection settings are present, and editing an env file does not update a running container's environment. Name any actual restart requirement rather than promising restart-free activation. Assign bounded test inputs/target preparation to the team, not implicitly to the User; a written test order is not a prepared environment.
3. Define a finite acceptance path from the agreed user workflow and safety requirements before scheduling verification. Explain its purpose to the User in product terms: install and import, use the feature, repeat/restart, disable/re-enable, and recover without damaging existing data, as applicable. Map every additional check to an accepted requirement or a concrete changed-code risk; do not introduce speculative test research or duplicate integrated checks as extra gates. Follow the README's exact commands against a safely prepared, already initialized and populated installation, including agreed failure cases and UI behavior. Reuse valid exact-commit evidence; rerun affected checks when the tested code or environment changes and retain independent review. Neither compilation nor a mock-only test establishes operator usability.
4. Record the execution boundary supplied at approval in the plan and every phase ticket before release. If the User reserves live application for himself and permits local tests, assign bounded test preparation to the team, name the local test machine as the permitted target, and keep deployment outside the team’s task; do not reopen that settled decision or inherit an older remote-host permission. Require the executing role to verify the actual Docker target, available capacity and occupied ports before starting disposable instances. Isolate container/network/volume names, image tags, published ports and host bind mounts explicitly; a different Compose project name alone does not isolate a deployment. Prefer no published ports, otherwise free loopback-only ports; use synthetic credentials, bound resource use, preserve existing services and data, and clean up only resources owned by the test.
5. Verify actual image identity and feature capability, not mutable or SNAPSHOT tags alone. Before scheduling integrated acceptance, establish the obtainable baseline/target artifacts and real dependency services, and compare the maintained application's start contract with the installer's compatibility guards. When the User confirms baseline references and provides an authorized credential source, verify registry metadata without displaying credentials before treating access as resolved; distinguish accessible manifests, locally acquired images, compatibility checks and integrated acceptance in the handoff. Freeze acquired baseline identities and keep target builds separately named so mutable tags cannot replace the starting point during verification. Use the authenticated acquisition procedure in the operator acceptance reference. Do not replace an authentic pre-feature baseline with a feature build stripped for testing, or real dependency services with idle placeholders; these substitutions can make a lifecycle test pass without exercising the promised upgrade. Distinguish targeted app restart/image replacement from main-database migration; restoring an old image does not reverse a schema change. Make the accepted scope and rollback limits explicit before promising safe installation.
